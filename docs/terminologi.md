# Terminologi

| Term | Definition | Kommentar |
|---|---|---|
| XLPM | En etablerad projektstyrningslogik som ofta förknippas med faser, beslutspunkter, roller och tydliga leverabler. | Boken använder XLPM som igenkännbar referenspunkt, inte som något som ska avfärdas. |
| Fasbaserat kravarbete | Kravarbete där en stor del av analys och dokumentation görs före utveckling. | Kan skapa tydlighet, men kan också låsa antaganden för tidigt. |
| Agilt kravarbete | Kravarbete som sker närmare team, produktägare och löpande prioritering. | Betyder inte kravlöst arbete. |
| Funktionellt krav | Beskriver vad systemet, tjänsten eller processen ska göra. | Skiljs från exempelvis tekniska kvalitetskrav. |
| Kravanalytiker | Person som hjälper verksamhet och IT att förstå, analysera och formulera krav. | I boken representeras rollen av Karin. |
| Verksamhetsanalytiker | Roll som analyserar verksamhetens behov, processer, regler och mål. | Överlappar ofta kravanalytikerrollen. |
| Produktägare | Roll som ansvarar för prioritering och värde i produkt- eller utvecklingsflöde. | Karin samarbetar nära produktägaren. |
| Backlogg | Prioriterad lista över behov, arbete eller förändringar som kan utvecklas stegvis. | Ska inte ersätta allt kravtänkande. |
| User story | Kort beskrivning av behov eller funktion ur användar-/verksamhetsperspektiv. | Används där det passar, inte som enda kravform. |
| Acceptanskriterium | Villkor som behöver vara uppfyllt för att krav eller story ska anses accepterad. | Kopplar krav till testbarhet. |
| Refinement | Löpande arbete med att förtydliga och förbereda backloggposter. | Förklaras mer i senare kapitel. |
| Spårbarhet | Möjlighet att följa samband mellan behov, krav, beslut, utveckling och test. | Ska vara tillräcklig, inte maximal. |
| Rollskifte | Förändringen i kravanalytikerns arbetssätt när organisationen går från fasbaserat till agilt kravarbete. | Handlar om ansvar och arbetsform, inte om att rollen försvinner. |
| Kravfacilitering | Att leda och strukturera kravdialoger, analyser och beslut så att flera personer kan förstå och agera på krav. | En central förmåga i kapitel 2. |
| Gemensam förståelse | Att berörda personer har tillräckligt likartad bild av behov, regler, mål, lösningsutrymme och acceptans. | Betyder inte att alla tycker samma sak. |
| Levande kravunderlag | En sammanhållen men uppdaterbar samling artefakter som tillsammans beskriver behov, krav, beslut, regler och acceptans. | Introduceras i kapitel 3 som alternativ till att lägga all kravkunskap i en kravspecifikation. |
| Artefakt | Ett konkret kravrelaterat underlag, till exempel backloggpost, processbild, beslutslogg eller acceptanskriterium. | Används som neutralt ord för olika typer av dokumenterat stöd. |
| Stabilt underlag | Kravinformation som behöver vara tydlig, beständig, återfinnbar och ofta spårbar över tid. | Exempel är mål, avgränsningar, regler, begrepp och viktiga beslut. |
| Arbetsnära underlag | Kravinformation som behövs för nästa utvecklingssteg och kan förändras när teamet lär sig mer. | Exempel är backloggposter, acceptanskriterier och frågor inför refinement. |
| Utforskande underlag | Information som ännu inte är färdig, till exempel hypoteser, antaganden, alternativ och öppna frågor. | Hjälper teamet undvika falsk säkerhet. |
| Behovshypotes | En tydlig formulering av vad vi tror att en målgrupp behöver och varför det är viktigt. | Används när behovsbilden är osäker och kravet ännu inte bör låsas. |
| Effektmål | Beskriver vilken verksamhets- eller användareffekt en förändring ska bidra till. | Hjälper kravdialogen fokusera på nytta snarare än bara leverans. |
| Antagande | Något vi tror är sant men ännu inte har tillräckligt stöd för. | Bör märkas upp så att det inte misstas för fakta, beslut eller färdigt krav. |
| Kravkandidat | En möjlig kravformulering som behöver förädlas, prioriteras eller kvalitetssäkras innan den behandlas som redo. | Används för att undvika att tidiga idéer får för hög status. |
| Kravdialog | Strukturerad dialog med intressenter för att skapa gemensam förståelse, inte bara samla in önskemål. | Fördjupas i kapitel 5 som central arbetsform för agilt kravarbete. |
| Intressentperspektiv | Ett perspektiv från en grupp eller roll som påverkas av, ansvarar för eller behöver förstå kravet. | Hjälper Karin undvika att “verksamheten” behandlas som en enda röst. |
| Faciliterad fördjupning | När kravanalytikern hjälper gruppen att gå från allmänna utsagor till konkreta behov, regler, exempel, beslut och frågor. | Används i kravdialoger för att göra kravunderlaget mer användbart. |

| Kravnivå | Olika abstraktionsnivåer i kravarbete, från effekt och större funktion till utvecklingsbar del och regel. | Hjälper Karin hålla ihop helhet och detalj. |
| Nedbrytning | Analysarbete där större funktionella krav delas upp i mindre, prioriterbara och testbara delar. | Ska inte reduceras till att klippa isär en kravspecifikation. |
| Vertikal kravskiva | En avgränsad funktionell del som går genom användning, verksamhetslogik och teknik så att teamet kan lära av ett fungerande flöde. | Används för att undvika ren komponent- eller teknikuppdelning. |
| Redo nog | Tillräckligt tydligt kravunderlag för nästa utvecklingssteg, med kända osäkerheter synliga. | Ett alternativ till tanken att kravet måste vara färdigt för alltid. |
| User story | En mindre utvecklingsbar kravdel uttryckt ur användar- eller aktörsperspektiv. | Används pragmatiskt; allt arbete behöver inte formuleras som user story. |
| Testbarhet | Att ett krav kan verifieras genom test, granskning eller demonstration. | Testbarhet är en central del av kravkvalitet. |
| Definition of Done | Teamets gemensamma kvalitetsvillkor för när arbete kan betraktas som klart. | Skiljs från acceptanskriterier, som gäller en specifik funktionell del. |
| Testfall | En konkret beskrivning av hur ett beteende ska verifieras. | Mer detaljerat än acceptanskriterium. |
| Negativt acceptanskriterium | Ett acceptanskriterium som beskriver vad som inte får hända eller vad systemet ska hindra. | Viktigt vid behörighet, sekretess, regelstyrning och felhantering. |
| Verksamhetsregel | Ett villkor, en begränsning eller en princip som styr hur verksamhet eller system ska bete sig. | Skiljs från funktionellt krav, som beskriver vad systemet ska kunna göra. |
| Undantag | En situation där huvudregeln inte räcker eller där ett särskilt utfall ska gälla. | Ska sorteras efter konsekvens, inte bara samlas i en lång lista. |
| Beslutstabell | En tabell som visar vilka villkor som leder till vilka utfall. | Används för att göra regelstyrd komplexitet synlig och testbar. |
| Regelkatalog | En samlad beskrivning av återanvända eller särskilt viktiga verksamhetsregler. | Passar när regler används i flera flöden eller kräver tydligt ägarskap. |


| Spårbarhetsbehov | De frågor och samband som spårbarheten behöver hjälpa organisationen att förstå. | Utgår från syfte och användning, inte från verktygets fält. |
| Tillräcklig spårbarhet | Spårbarhet som räcker för beslut, test, ändring, förvaltning och uppföljning utan onödig administration. | Bokens rekommenderade princip för agil myndighetskontext. |
| Beslutsspår | Kort dokumentation av viktiga vägval, alternativ, motivering och konsekvens. | Hjälper organisationen förstå varför ett krav eller beteende ser ut som det gör. |
| Teamnära kravarbete | Kravarbete som bedrivs i tät kontakt med de personer som prioriterar, utvecklar, testar, designar, förvaltar och använder lösningen. | Handlar om arbetsmönster, inte bara organisatorisk placering. |
| Ansvarsyta | Ett område där en roll har särskilt ansvar att bidra med kvalitet, frågor, beslut eller struktur. | Används för att tydliggöra överlappande ansvar mellan roller. |
| Refinement | Löpande arbete med att förtydliga, dela upp, prioritera och förbereda backloggposter så att de kan utvecklas kontrollerat. | Behandlas som en viktig rytm för kravförädling, inte bara uppskattning. |
| Sen förändring | En ändring, ny insikt eller ny avgränsning som uppstår efter att kravunderlag eller utvecklingsarbete redan kommit en bit. | Ska analyseras, inte reflexmässigt avvisas eller accepteras. |
| Konsekvensanalys | Strukturerad analys av påverkan på krav, test, lösning, arkitektur, förvaltning, risk och prioritet. | Hjälper produktägare och team att fatta beslut. |
| Ändringsdialog | Lättviktig dialog där berörda roller förstår, värderar och beslutar hur en förändring ska hanteras. | Ersätter inte formell styrning när sådan behövs. |

| Verktygslåda | Samling av arbetssätt, frågor, checklistor och mallar som kravanalytikern väljer utifrån situation. | Introduceras i kapitel 12 som praktiskt stöd, inte som obligatorisk metod. |
| Arbetsmönster | Återkommande sätt att skapa tydlighet i en viss typ av kravsituation. | Hjälper kravanalytikern att agera konsekvent utan att följa en tung process. |
| Beslutslogg | Enkel dokumentation av viktiga beslut, bakgrund, påverkan och öppna följder. | Används för spårbarhet utan omfattande dokumentationsbörda. |
| Spårbarhetsmatris light | Enkel koppling mellan behov, krav/backloggpost, regel/beslut, acceptans/test och status. | Ska hållas liten, aktiv och användbar. |
